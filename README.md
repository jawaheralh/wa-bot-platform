# منصة بوت واتساب — نظام وحدات متعدد المنشآت

بوت واتساب ذكي يخدم عدة منشآت (عيادات، مطاعم، صالونات، متاجر) في تشغيل واحد.
كل منشأة لها رقمها ونبرتها وقاعدة معرفتها، والوظائف مقسّمة إلى **وحدات** تُفعَّل
لكل منشأة على حدة من صفحة الأدمن.

الفكرة التجارية: تبدأ المنشأة باشتراك «استفسارات + شكاوى»، وتُفعَّل لها الحجوزات
لاحقاً بضغطة زر — بلا تعديل كود ولا إعادة نشر ولا مساس بالمنشآت الأخرى.

---

## التشغيل

```bash
npm install
npm run setup                 # معالج تفاعلي يسألك عن المفاتيح ويتحقق منها
npm run seed                  # منشأتان تجريبيتان + أدمن النظام
npm start
```

**`npm run setup`** يغنيك عن تحرير `.env` يدوياً: يسألك عن كل قيمة بالعربي،
و**يختبر المفاتيح بنداء حقيقي** قبل الحفظ (مفتاح ناقص أو منتهٍ يُرفض فوراً
بدل أن تكتشفيه من صمت البوت أمام عميل). يحفظ التعليقات والترتيب، ويأخذ
نسخة احتياطية في `.env.backup`، ويولّد سرّ جلسة قوياً إن كان ضعيفاً.

- Enter على أي حقل = إبقاء قيمته الحالية
- `-` ثم Enter = مسح القيمة
- `npm run check` = عرض الحالة بلا تعديل

لوحة التحكم على **<http://127.0.0.1:4000>**

`npm run seed` يطبع كلمات مرور **عشوائية مرة واحدة** — احفظيها فوراً:

```
  admin    xK7mP2qR9tLw    أدمن النظام
  noor     b4Nz8vHy3cTe    عيادة النور
  rukn     Qw9fJ5xM2kPs    مطعم الركن
```

لا توجد كلمة مرور ثابتة في الكود ولا في هذا الملف. الثابتة تسري إلى الإنتاج
ثم تُنشر مع المستودع، فيدخل كل من قرأه لوحة التحكم.

أوامر أخرى:

```bash
npm run setup     # تعديل المفاتيح
npm run check     # عرض حالة الإعدادات بلا تعديل
npm test          # ٢٠٠ اختبار
npm run build     # فحص الأنواع (tsc)
npm run dev       # إعادة تشغيل تلقائية عند التعديل
npm run sim -- "وش أسعاركم؟"          # محادثة تجريبية من الطرفية
npm run sim -- --tenant 2             # وضع تفاعلي مع منشأة أخرى
```

`npm run sim` يشغّل **نفس** محرّك البوت بالضبط عبر مزوّد المحاكي، ويحتاج
`ANTHROPIC_API_KEY` حقيقياً — فما تريه فيه هو ما سيراه العميل على واتساب.

## ربط رقم عبر Baileys (للتجربة والعروض)

هذه أسرع طريقة لتجربة النظام برقم واتساب عادي. **غير رسمية** ولا تصلح للإنتاج —
واتساب قد يوقف الرقم.

1. في `.env`: `WA_PROVIDER=baileys`
2. `npm start` — يُطبع رمز QR في الطرفية لكل منشأة نشطة.
3. على الجوال: واتساب ← الإعدادات ← **الأجهزة المرتبطة** ← ربط جهاز ← امسحي الرمز.
4. عند نجاح الاتصال يُطبع: «اتصل رقم المنشأة … بواتساب».

الجلسة تُحفظ في `data/baileys/<رقم المنشأة>/` فلا تحتاجين المسح في كل تشغيل.
لحذف الربط وإعادة المسح: احذفي مجلد المنشأة وأعيدي التشغيل.

كل منشأة جلسة مستقلة تماماً: مسح QR لعيادة النور لا يمسّ مطعم الركن.

> الإصدار المثبَّت `@whiskeysockets/baileys@7.0.0-rc14` (لا يوجد 7.x مستقر بعد).
> إن واجهتِ عطلاً بعد تحديث واتساب، جرّبي `npm i @whiskeysockets/baileys@6.7.24`.

## ربط رقم 9200 عبر Cloud API (الإنتاج)

هذه الطريقة الرسمية. الرقم الموحّد 9200 رقم أرضي لا يستقبل رسائل SMS، لذلك
**التحقق يتم بالمكالمة الصوتية** — وهذه أهم نقطة في العملية كلها.

### ١. تجهيز الحساب في Meta

1. افتحي <https://business.facebook.com> وأنشئي حساب أعمال (Meta Business Account)
   باسم شركتك، ووثّقيه بالسجل التجاري.
2. من <https://developers.facebook.com/apps> أنشئي تطبيقاً من نوع **Business**.
3. أضيفي منتج **WhatsApp** للتطبيق.

### ٢. إضافة الرقم والتحقق بالمكالمة

1. في لوحة WhatsApp ← **API Setup** ← `Add phone number`.
2. أدخلي الرقم بصيغة دولية: `+966 9200xxxxx`.
3. في خطوة التحقق اختاري **Voice call** لا SMS.
4. Meta تتصل بالرقم وتنطق رمزاً من ستة أرقام **بالإنجليزية**. جهّزي شخصاً عند
   السنترال يرد ويكتب الرمز، أو حوّلي الرقم مؤقتاً لجوال يرد عليه.
   الرمز يُنطق مرة أو مرتين فقط — إن فاتك، اطلبي مكالمة جديدة.
5. بعد التحقق ينتقل الرقم لحالة `Connected`، وتظهر له قيمة **Phone number ID**.
6. سجّلي اسماً ظاهراً (Display name) — يحتاج مراجعة من Meta تستغرق يوماً أو يومين.

### ٣. الإعداد في المشروع

في `.env`:

```bash
WA_PROVIDER=cloud
WA_VERIFY_TOKEN=نص-تختارينه-أنتِ        # أي نص، يُستعمل مرة عند ربط الـwebhook
WA_APP_SECRET=...                       # App Settings ← Basic ← App Secret
WA_ACCESS_TOKEN=...                     # توكن دائم من System User (لا المؤقت)
WA_GRAPH_VERSION=v23.0
```

> التوكن المؤقت في صفحة API Setup ينتهي خلال ٢٤ ساعة. للإنتاج أنشئي
> **System User** من Business Settings، أعطيه صلاحية `whatsapp_business_messaging`،
> وولّدي منه توكناً دائماً.

ثم في صفحة الأدمن، حرّري المنشأة وضعي **معرّف الرقم في Cloud API**
(`Phone number ID`) — هو مفتاح توجيه الرسائل لهذه المنشأة.

### ٤. ربط الـwebhook

الخادم يحتاج عنوان HTTPS عاماً. محلياً استعملي نفقاً:

```bash
cloudflared tunnel --url http://localhost:4000
```

ثم في Meta: WhatsApp ← Configuration ← Webhook:

- **Callback URL**: `https://<عنوانك>/webhook/whatsapp`
- **Verify token**: نفس `WA_VERIFY_TOKEN`
- اضغطي `Verify and save` — يجب أن تظهر «نجح تحقق webhook من Meta» في سجلك.
- في `Webhook fields` فعّلي **messages**.

### ٥. التحقق من العمل

أرسلي رسالة من جوالك للرقم. في السجل يجب أن يظهر سطر «رسالة واردة»، وفي لوحة
التحكم تظهر المحادثة.

**ملاحظة أمنية:** كل حمولة تصل الـwebhook يُتحقق من توقيعها بـHMAC-SHA256 على
الجسم الخام. الحمولة بلا توقيع صحيح تُرفض بـ401 — وهذا ما يمنع أي أحد يعرف
عنوانك من حقن رسائل باسم عملائك.

## الفريق: أكثر من موظف على نفس الرقم

ثلاثة أدوار:

| الدور | يستطيع |
|---|---|
| **أدمن النظام** (`system`) | كل المنشآت، وتفعيل الوحدات وتعطيلها |
| **مالك المنشأة** (`tenant`) | كل شيء داخل منشأته: الموظفون، قاعدة المعرفة، إعدادات الوحدات، المحادثات |
| **موظف** (`agent`) | المحادثات والشكاوى والمواعيد فقط — لا يمسّ المعرفة ولا الوحدات ولا الموظفين |

التمييز ليس ترفاً: بدونه يستطيع أي موظف حذف حساب المالك أو تغيير قاعدة
المعرفة التي يتكلم بها البوت مع كل العملاء.

من اللوحة ← **الموظفون** (يظهر للمالك وأدمن النظام):

- **إضافة موظف** باسم مستخدم وكلمة مرور ورقم جوال اختياري.
- **رقم التنبيهات** لكل موظف — تصله إشعارات الشكاوى العاجلة والتحويلات.
- **تعطيل** بدل الحذف: الحساب يبقى فتبقى ردوده السابقة منسوبة له في سجل
  المحادثات. الجلسة المفتوحة للحساب المعطَّل تسقط فوراً لا عند انتهاء الكوكي.
- آخر مالك نشط لا يمكن تعطيله ولا تنزيله لموظف، ولا يعطّل المالك حسابه هو.

### الإسناد ومنع الرد المزدوج

- كل محادثة لها **مسؤول** يُختار من قائمة الفريق، ويظهر في جدول المحادثات.
- من يرد يدوياً على محادثة غير مُسندة **تُسند له تلقائياً**.
- كل رد يُسجَّل باسم كاتبه: يظهر «منى» في سجل المحادثة لا «الموظف».
- فتح محادثة يسجّل حضورك. لو فتحها زميلك قبلك خلال دقيقتين يظهر لك تحذير
  أحمر باسمه، ولو كانت مُسندة لغيرك يطلب منك تأكيداً قبل الإرسال.
- **التنبيهات موجَّهة:** المحادثة المُسندة تنبّه صاحبها وحده؛ غير المُسندة
  تنبّه كل الفريق. توجيه التنبيه للمسؤول يمنع تحوّله لضجيج يتجاهله الجميع
  لأن كلاً منهم يفترض أن الآخر يتابع. وإن كان المُسند إليه معطَّلاً أو بلا
  رقم، يُنبَّه الفريق كله بدل ضياع التنبيه.

> هذا حضور خفيف بلا websockets — يكفي أن يرى الثاني «منى فتحتها قبل ٢٠ ثانية»
> ليتوقف قبل أن يصل العميل ردّان. لا يوجد «منى تكتب الآن» لحظي.

## إضافة منشأة جديدة

من صفحة الأدمن (بحساب أدمن النظام) ← **كل المنشآت** ← نموذج «إضافة منشأة»:

| الحقل | الشرح |
|---|---|
| اسم المنشأة | يظهر للعميل في ردود البوت |
| رقم واتساب | مفتاح التوجيه. أي صيغة تُقبل (`+966…` أو `00966…`) وتُطبَّع تلقائياً |
| النبرة | رسمية (صيغة الجمع، بلا إيموجي) أو ودّية («هلا والله»، «أبشر») |
| رقم الموظف | تصله تنبيهات الشكاوى العاجلة والتحويلات |
| معرّف الرقم في Cloud API | مطلوب في الإنتاج فقط |
| مستخدم أدمن المنشأة | حساب يرى منشأته فقط |

عند الإنشاء تُفعَّل الوحدات الأساسية تلقائياً، وتُنشأ صفوف كل الوحدات في
`tenant_modules`. بعدها:

1. من **قاعدة المعرفة** أدخلي النص الحر والأسئلة الشائعة. *هذه أهم خطوة* —
   البوت لا يقول إلا ما هنا، وما ليس هنا يحوّله للموظف.
2. من **الوحدات** فعّلي ما اشترته المنشأة واضبطي إعداداته.
3. اربطي الرقم (QR أو Cloud API).

## كيف أكتب وحدة جديدة

الوعد المعماري: **ملف واحد + سطر واحد**. لا تعديل في محرّك البوت، ولا في
قاعدة البيانات، ولا في صفحة الأدمن.

### ١. اكتبي `src/modules/loyalty.ts`

```ts
import type { BotModule, ModuleContext, ToolDefinition, ToolResult } from './types.ts';
import { readString } from './types.ts';
import { SQL_NOW } from '../time.ts';

export const loyaltyModule: BotModule = {
  name: 'loyalty',                    // لا يتغير بعد الإطلاق — مخزَّن في القاعدة
  titleAr: 'نقاط الولاء',
  descriptionAr: 'يتابع نقاط العملاء ويخبرهم برصيدهم ومتى يستحقون مكافأة.',
  core: false,                        // اختيارية ⇐ معطّلة افتراضياً

  // تُنفَّذ عند كل إقلاع، حتى لو كانت الوحدة معطّلة لكل المنشآت
  tables: [
    `CREATE TABLE IF NOT EXISTS loyalty_points (
      id          INTEGER PRIMARY KEY AUTOINCREMENT,
      tenant_id   INTEGER NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
      customer_wa TEXT    NOT NULL,
      points      INTEGER NOT NULL DEFAULT 0,
      updated_at  TEXT    NOT NULL DEFAULT (${SQL_NOW}),
      UNIQUE (tenant_id, customer_wa)
    )`,
  ],

  defaultConfig: () => ({ pointsPerVisit: 10, rewardAt: 100 }),

  validateConfig(input) {
    const raw = (input ?? {}) as Record<string, unknown>;
    return {
      pointsPerVisit: Math.max(1, Number(raw.pointsPerVisit) || 10),
      rewardAt: Math.max(10, Number(raw.rewardAt) || 100),
    };
  },

  // يُضاف للـprompt فقط إذا كانت الوحدة مفعّلة لهذه المنشأة
  systemPrompt(ctx) {
    return `## نقاط الولاء
كل زيارة = ${ctx.config.pointsPerVisit} نقطة، والمكافأة عند ${ctx.config.rewardAt} نقطة.
إذا سأل العميل عن رصيده استعمل get_points. لا تَعِد بمكافأة قبل بلوغ الحد.`;
  },

  tools(): ToolDefinition[] {
    return [{
      name: 'get_points',
      description: 'يستعلم عن رصيد نقاط العميل الحالي.',
      input_schema: { type: 'object', properties: {} },
    }];
  },

  async runTool(name, input, ctx: ModuleContext): Promise<ToolResult> {
    if (name !== 'get_points') return { content: `أداة غير معروفة: ${name}`, isError: true };

    const row = ctx.db
      .prepare('SELECT points FROM loyalty_points WHERE tenant_id = ? AND customer_wa = ?')
      .get(ctx.tenant.id, ctx.conversation.customer_wa) as { points: number } | undefined;

    const points = row?.points ?? 0;
    const remaining = Number(ctx.config.rewardAt) - points;
    return {
      content: remaining > 0
        ? `رصيد العميل ${points} نقطة، وباقي ${remaining} نقطة للمكافأة. أبلغه بذلك.`
        : `رصيد العميل ${points} نقطة وهو يستحق المكافأة. أبلغه وحوّله للموظف لصرفها.`,
    };
  },

  // اختياري: مسارات API لصفحة الأدمن، تُركَّب تلقائياً
  routes(app, deps) {
    app.get('/api/tenants/:tenantId/loyalty', async (request) => {
      const tenantId = Number((request.params as { tenantId: string }).tenantId);
      const user = request.user;
      if (!user || (user.role !== 'system' && user.tenantId !== tenantId)) {
        throw Object.assign(new Error('لا تملك صلاحية على هذه المنشأة.'), { statusCode: 403 });
      }
      return deps.db
        .prepare('SELECT * FROM loyalty_points WHERE tenant_id = ? ORDER BY points DESC')
        .all(tenantId);
    });
  },

  // اختياري: مهمة دورية كل دقيقة للمنشآت المفعِّلة فقط
  // async onTick(tenant, config, deps) { … },
};
```

### ٢. سجّليها في `src/modules/registry.ts`

```ts
import { loyaltyModule } from './loyalty.ts';

export const MODULES: BotModule[] = [
  inquiriesModule, complaintsModule, handoffModule, bookingsModule,
  loyaltyModule,        // ← هذا كل شيء
];
```

### ٣. هذا كل شيء

عند الإقلاع التالي تلقائياً:

- يُنشأ جدول `loyalty_points`.
- يظهر صف للوحدة في `tenant_modules` لكل منشأة (معطّل).
- تظهر بطاقة رمادية في شاشة **الوحدات** لكل أدمن منشأة، عليها وصفك وزر
  «تواصل معنا على واتساب».
- بعد أن يُفعّلها أدمن النظام: تظهر إعداداتها في نموذج مولَّد تلقائياً من
  `defaultConfig()`، ويرى النموذج أداة `get_points` وتعليماتك.
- قبل التفعيل: **النموذج لا يعرف أن الوحدة موجودة أصلاً.**

لإظهار اسم عربي لمفتاح إعداد جديد في الواجهة، أضيفي سطراً في `LABELS`
داخل `public/js/views/modules.js`. المفتاح غير المذكور يظهر باسمه البرمجي.

### قواعد يجب احترامها

- **العزل:** كل استعلام يجب أن يحمل `tenant_id`. لا استثناء.
- **التوقيت:** استعملي `SQL_NOW` و `SQL_TODAY` من `time.ts`، لا `datetime('now')`
  المجرّدة — الفرق ثلاث ساعات ولا يظهر إلا في الإنتاج.
- **لا تثقي بالنموذج:** استعملي `readString` و `readEnum` و `readNumber` من
  `types.ts` بدل قراءة المدخلات مباشرة.
- **نتيجة الأداة تُكتب للنموذج لا للعميل:** اكتبيها كتعليمة («أبلغ العميل بأن…»)
  لا كرسالة جاهزة.
- **القرار الحرج منطق برمجي:** التصعيد والتعارض والصلاحيات تُقرَّر في الكود، لا
  تُترك للنموذج.

## سلوك البوت

- عربي سعودي مختصر، والنبرة حسب إعداد المنشأة.
- يحفظ آخر ٢٠ رسالة كسياق (قابل للضبط بـ`HISTORY_LIMIT`).
- لا يخترع معلومة: ما ليس في قاعدة المعرفة يُحوَّل للموظف.
- يفهم «بكرة» و«بعد بكرة» و«الأحد الجاي»، والغامض يسأل عنه.
- الشكوى عالية الخطورة تنبّه الموظف فوراً على واتساب وتظهر في اللوحة.
- **الوضع الصامت:** إذا ردّ الموظف يدوياً (من جواله أو من اللوحة) يصمت البوت
  ساعتين تلقائياً حتى لا يقاطعه. المدة بـ`SILENT_MINUTES`.
- الرسائل الصوتية تُحوَّل لنص إن وُجد `OPENAI_API_KEY`؛ وإلا يطلب البوت رسالة نصية.

## الطلبات وإبلاغ العميل تلقائياً

وحدة **الطلبات** (اختيارية) تستقبل طلبات الخدمة — صيانة، اشتراك، عرض سعر،
زيارة، توريد — برقم مرجعي `TLB-2026-000042`، وتتابعها بخمس حالات:
جديد ← قيد التنفيذ ← بانتظار العميل ← منجز / ملغى.

**الأهم: العميل يُبلَّغ تلقائياً على واتساب بكل تغيير في حالة طلبه.**

```
تحديث على طلبك لدى «اسم منشأتك»

رقم الطلب: TLB-2026-000002
النوع: صيانة
الحالة: قيد التنفيذ

بدأنا العمل على طلبك.
ملاحظة: الفني في الطريق، الوصول خلال ساعتين
```

نفس الآلية تعمل على **الشكاوى** أيضاً.

تفاصيل مقصودة في التصميم:

- **لا يُزعج العميل برسالتين لنفس الحالة**: عمود `notified_status` يمنع
  التكرار حين يحفظ الموظف مرتين. إزعاج كهذا يجعل العميل يحظر الرقم.
- **الملاحظة تخصّ حالتها**: «نحتاج تأكيد موعد الفني» كُتبت وهو بانتظار
  العميل، فلا تُلصق برسالة «اكتمل طلبك» فتناقضها.
- **نتيجة الإرسال تُعرض صراحةً**: عمود «أُبلغ العميل» في الجدول، وزر إعادة
  إرسال عند الفشل. لا يُوهَم الموظف أن العميل عَلِم وهو لم يعلم.
- **لا رسالة عند التسجيل**: البوت يذكر الرقم في ردّه أثناء المحادثة، فرسالة
  ثانية تكرار.

> ⚠️ **على Cloud API** لا يصل التحديث إذا مرّ أكثر من ٢٤ ساعة على آخر رسالة
> من العميل — قاعدة Meta لا قيد فينا. يظهر الفشل في اللوحة، والحل هو قالب
> معتمد من Meta (غير مبني بعد). على Baileys يصل دائماً.

## الخصوصية وحماية البيانات

**هذا قسم تقني وليس استشارة قانونية.** رسائل عملائك بيانات شخصية، ومعالجتها
تخضع لنظام حماية البيانات الشخصية (PDPL) وجهته سدايا — سواء كان النظام
داخلياً أو عاماً. راجعي مختص امتثال سعودي.

### ما يغادر جهازك فعلاً

| | |
|---|---|
| رقم العميل | **لا يغادر** |
| اسم العميل | **لا يغادر** |
| نص الرسالة | يُرسل إلى Anthropic — ضروري للرد، وهو **نقل عابر للحدود** |

مُختبَر باعتراض الحمولة قبل الإرسال، لا بالقراءة من الكود.
وفي وضع `READ_ONLY=1` أو بلا `ANTHROPIC_API_KEY` **لا يغادر شيء إطلاقاً**.

### الأدوات في شاشة «الخصوصية» (لمالك المنشأة)

- **مدة الاحتفاظ**: تُحذف نصوص المحادثات الأقدم من المدة تلقائياً كل يوم.
  الشكاوى والطلبات والمواعيد **لا تُحذف** — سجلات عمل لها قيمة إدارية،
  بينما نصوص المحادثات أكثر حساسية وأقل فائدة بعد انتهاء التعامل.
  صفر = بلا حد.
- **حق الاطلاع**: تصدير كل ما لدى المنشأة عن رقم عميل كملف JSON. التنزيل
  يتم في المتصفح فلا تغادر البيانات الجهاز.
- **حق المحو**: حذف فعلي — لا تعليم — لكل بيانات العميل. يقتصر على المنشأة
  المطلوبة: العميل قد يتعامل مع منشأتين، وطلبه لدى إحداهما لا يخوّل حذف
  بياناته لدى الأخرى.
- **سجل التدقيق**: من فعل ماذا ومتى — الدخول، وتغيير الحالات، والردود
  اليدوية، وتعديل المعرفة، وحذف البيانات. اسم المستخدم يُنسخ نصاً فيبقى
  بعد حذف الحساب، والسجل لا يحتوي محتوى الرسائل.

الموظف (`agent`) لا يرى هذه الشاشة ولا مساراتها.

## وضع «عرض فقط» — قبل أن يتكلم النظام باسمك

```bash
READ_ONLY=1
```

يستقبل رسائل العملاء ويحفظها ويعرضها في اللوحة، **ولا يُرسل شيئاً إطلاقاً**:
لا رد بوت، ولا رد موظف، ولا تنبيه واتساب، ولا تذكير موعد. ويظهر شريط أصفر
في اللوحة حتى لا يُنسى، ومحاولة الرد اليدوي تُرفض برسالة واضحة بدل أن
يُوهَم الموظف أن رده وصل.

المنع في طبقة المزوّد لا في المحرّك: أي مسار إرسال جديد يُكتب مستقبلاً يمر
منها حتماً، فلا يستطيع أحد أن ينسى احترام الوضع.

استعمليه لترى ما يصل رقمك فعلاً وتبني قاعدة المعرفة على أسئلة عملائك
الحقيقية، قبل أن تسمحي للنظام بالرد.

---

## هل الربط يضرّ الرقم؟

| المزوّد | الخطر |
|---|---|
| **Cloud API** (الرسمي) | **لا خطر.** هذا منتج Meta نفسها والطريق المعتمد |
| **Baileys** (QR) | **خطر حقيقي.** عميل غير رسمي بهندسة عكسية، وواتساب يوقف الأرقام بسببه |

**القاعدة:** Baileys لأرقام التجربة الثانوية فقط. الرقم الموحّد أو أي رقم
رسمي يُربط بـCloud API حصراً.

ولأن الخطأ هنا لا يُصلَح، منعه النظام برمجياً: أي منشأة لها
`wa_phone_number_id` (أي مسجَّلة في Meta) **يرفض النظام فتح جلسة QR لها**
ويسجّل السبب، حتى لو كان `WA_PROVIDER=baileys`.

ما يؤثر على Cloud API ليس الحظر بل **تقييم الجودة**: لو حظر عملاؤك رسائلك
أو أبلغوا عنها، تخفض Meta حدود إرسالك. وهذا سبب إضافي لتبدئي بـ`READ_ONLY=1`
ولا ترد إلا بعد أن تطمئني لجودة ردود البوت.

## التشغيل في GitHub Codespaces (بلا طرفية محلية)

الطريقة الأسهل لفتح النظام من أي جهاز أو متصفح:

**مستودع GitHub ← زر `Code` الأخضر ← تبويب `Codespaces` ← `Create codespace on main`**

تُجهَّز البيئة تلقائياً (Node، الاعتماديات، قاعدة البيانات، سرّ جلسة عشوائي،
وأول حساب أدمن بكلمة مرور تُطبع مرة واحدة). ثم في الطرفية داخل المتصفح:

```bash
npm start
```

يُفتح المنفذ 4000 تلقائياً في تبويب معاينة.

### الخصوصية

المنفذ **خاص افتراضياً** (`visibility: private` في `.devcontainer`): لا يصله
أحد إلا بتسجيل دخول حسابك على GitHub، حتى لو كان المستودع عاماً. الكود عام،
والبيانات ليست كذلك.

> `.env` و`data/` خارج git، فمفاتيحك وقاعدة بياناتك تبقى داخل الـCodespace
> ولا تُرفع. كل Codespace يولّد سرّ جلسته الخاص.

### حدود يجب معرفتها

- **ينام بعد ٣٠ دقيقة خمول** ويتوقف بعد ٣٠ يوماً — فهو للتطوير والتجربة
  والعرض، لا لخدمة عملاء على مدار الساعة.
- **٦٠ ساعة مجانية شهرياً** على الحساب الشخصي، ثم بالأجر.
- **الحذف يمحو `data/app.db`** — احتفظي بنسخة عبر `deploy/backup.sh` أو
  نزّلي الملف قبل حذف الـCodespace.
- **لا يصلح كـwebhook لـCloud API** لأنه ينام. للإنتاج استعملي خادماً.

المزوّد يُضبط على `simulator` افتراضياً داخل الـCodespace: لا اتصال بواتساب
حتى تختاري ذلك صراحةً.

## النشر على خادم

النظام خفيف جداً — **١٣ ميجا رام** وقاعدة بيانات بالكيلوبايتات — فأصغر خادم يكفيه.

### ما لا يصلح

الاستضافات المجانية من نوع PaaS (Render وKoyeb وأمثالها في خططها المجانية)
**لا تصلح** لسببين قاتلين:

- **تنام بعد خمول**: رسالة عميل تصل أثناء النوم تفشل، وMeta تتوقف عن إعادة
  المحاولة بعد مدة. عميل أرسل ولم يصله رد أسوأ من عدم وجود النظام.
- **قرصها مؤقت**: `data/app.db` يُمسح عند كل نشر — تضيع المنشآت والشكاوى
  والمحادثات كلها.

المطلوب خادم حقيقي (VM) بقرص دائم. الخيارات المجانية الصالحة:
**Oracle Cloud Always Free** (دائم بلا مدة)، أو **Google Cloud e2-micro**،
أو **AWS free tier** (سنة). وأي VPS بخمسة دولارات يفي بالغرض.

### الإعداد لمرة واحدة

على خادم Ubuntu جديد:

```bash
sudo apt update && sudo apt install -y git sqlite3
sudo git clone <مستودعك> /opt/wa-bot
cd /opt/wa-bot
sudo bash deploy/setup.sh نطاقك.com
```

السكربت يثبّت Node وCaddy، وينشئ مستخدم خدمة محدود الصلاحيات، ويولّد
`SESSION_SECRET` عشوائياً، ويركّب خدمة `systemd` تعمل عند الإقلاع وتعيد
التشغيل تلقائياً عند أي تعطّل. Caddy يجلب شهادة HTTPS مجانية ويجددها وحده —
وهذا ما يجعل العنوان صالحاً لـwebhook من Meta.

ثم:

```bash
sudo -u wabot nano /opt/wa-bot/.env     # املئي المفاتيح
sudo -u wabot node src/seed.ts          # أول أدمن
sudo systemctl restart wa-bot
sudo journalctl -u wa-bot -f            # متابعة السجل
```

| الملف | وظيفته |
|---|---|
| `deploy/setup.sh` | الإعداد الكامل لمرة واحدة |
| `deploy/wa-bot.service` | خدمة systemd (تشغيل تلقائي + إعادة عند التعطّل) |
| `deploy/Caddyfile` | وكيل عكسي + HTTPS تلقائي |
| `deploy/backup.sh` | نسخة احتياطية متّسقة (WAL يمنع النسخ المباشر للملف) |

### النقل من جهازك للخادم

كل شيء في ملف واحد. انسخي `data/app.db` إلى `/opt/wa-bot/data/` وشغّلي
الخدمة — المنشآت وقاعدة المعرفة والشكاوى والمواعيد والموظفون وسجل المحادثات
كلها تنتقل كما هي. ثم حدّثي عنوان الـwebhook في Meta فقط.

### حراس الإنتاج

متغير `PUBLIC_URL` هو إشارة «هذا خادم على الإنترنت»، وعندها:

- **يرفض النظام الإقلاع** بسرّ جلسة ضعيف أو بقيمة المثال. من يعرف السرّ
  يزوّر كوكي جلسة لأي مستخدم، ولوحة على الإنترنت بسرّ منشور في مستودع ليست
  خطأً يُحتمل — فالرفض أصح من التحذير.
- **يصرخ السجل عند كل إقلاع** على أي حساب ما زال بكلمة مرور البذرة المنشورة
  في هذا الملف.

التطوير المحلي لا يتأثر: بلا `PUBLIC_URL` يعمل كل شيء كما هو.

## الحماية

- كلمات المرور مخزَّنة بـbcrypt (١٠ جولات)، وفشل الدخول يعيد 401 بنفس
  الرسالة سواء كان المستخدم موجوداً أم لا، فلا تُكشف الأسماء الموجودة.
- الجلسة كوكي موقَّع `httpOnly` + `sameSite=lax`، صلاحيته ١٢ ساعة.
- تحديد معدّل على `/api/login`: ٨ محاولات فاشلة من نفس المصدر ⇐ حظر ١٠ دقائق.
  الحدّ على عنوان المصدر لا على اسم المستخدم، وإلا عطّل مهاجمٌ حساب غيره.
- كل مسار تحت `/api/tenants/:tenantId` يمرّ على `requireTenantAccess` — أدمن
  المنشأة لا يصل لمنشأة غيره بأي حال.
- التفعيل والتعطيل لأدمن النظام وحده؛ مالك المنشأة يرى الوحدة المعطّلة ولا
  يستطيع تفعيلها، والموظف لا يرى شاشتَي المعرفة والوحدات أصلاً.
- حمولات Cloud API يُتحقق من توقيعها بـHMAC-SHA256 على الجسم الخام.
- الأسرار في `.env` وحده، وهو في `.gitignore`.

### ما لم يُطبَّق بعد

- لا مراقبة تنبّهك إذا توقفت الخدمة (systemd يعيد التشغيل لكنه لا يُخبرك).
- لا قوالب Meta المعتمدة، فتحديثات الطلبات تفشل خارج نافذة ٢٤ ساعة على Cloud API.
- لا إشعار خصوصية جاهز للعميل النهائي — نص يكتبه مختص، والنظام يوفّر الأدوات فقط.
- لا سجل «من غيّر ماذا» في إدارة الموظفين والإعدادات.
- لا HTTPS داخلياً؛ الخادم يفترض أنه خلف نفق أو وكيل عكسي.
- لا تشفير للبيانات في القرص — ملف SQLite نص عادي.
- لا سجل تدقيق لتغييرات الأدمن.

## ملاحظات تقنية

- Node ≥ ٢٢. ملفات `.ts` تعمل مباشرة بلا خطوة بناء (Node يجرّد الأنواع)،
  و`npm run build` فحص أنواع فقط.
- SQLite عبر `better-sqlite3` بوضع WAL. قاعدة البيانات ملف واحد في `data/`.
- التوقيت: `SQL_NOW = datetime('now','+3 hours')`. الرياض UTC+3 بلا توقيت صيفي.
- الأرقام المرجعية من جدول `counters`، متسلسلة لكل منشأة وسنة:
  `SHK-2026-000147` للشكاوى، `MWD-2026-000031` للمواعيد.
- إضافة مفتاح جديد لإعدادات وحدة لا تكسر المنشآت القائمة: الإعداد المخزَّن
  يُدمج فوق `defaultConfig()` عند القراءة.
- **إضافة عمود لجدول قائم:** `CREATE TABLE IF NOT EXISTS` لا يضيف أعمدة لجدول
  موجود، فقاعدة أُنشئت قبل ميزة جديدة تبقى ناقصة بصمت. الحل `ensureColumn`
  في `src/db/index.ts` — يقرأ `PRAGMA table_info` ويضيف الناقص عند كل إقلاع.
  الأعمدة المضافة بعد الإطلاق مسجّلة في `CORE_COLUMNS` داخل `db/schema.ts`،
  والوحدات تستعمل نفس الدالة لجداولها.
